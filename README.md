# 规则解释 AI（RAG 规则知识库 + 提示词方案）

面向 [CN]RXSEND 白藏测试服（SCP:RP / Garry's Mod）的规则解释 AI 完整方案。**核心是一套平台无关的 RAG 知识库与提示词工程**，不绑定任何特定框架——当前部署在 [AstrBot](https://github.com/AstrBotDevs/AstrBot)（QQ 机器人框架），同样可导入 Dify、FastGPT、AnythingLLM 等任何支持 RAG / 知识库问答的平台复用。

- **RAG 知识库**（`kb/`）：由服务器规则文档、人物图鉴 docx 转出的 77 个 Markdown 文件，含规则原文、32 个阵营档案、30 个人物分组档案（188 个角色），以及手工维护的速查层（阵营关系、术语别名、特殊事件、场景判定、处罚速查）。
- **系统提示词**（`prompt/`）：18 条判定准则、系统 persona、处罚速查表、39 条回归测试用例。除 AstrBot persona 格式外，判定准则与速查表对任何 LLM 应用直接可用。

> 配套插件 [astrbot_plugin_rule_card](https://github.com/wujunze/astrbot_plugin_rule_card)（把规则解释回复渲染成 SCP 档案风卡片图片，AGPL-3.0，独立仓库维护），本仓库为纯内容仓库，可独立使用。

- 规则版本：**2026/10/24**（见 `kb/07-第七章-规则版本改动记录.md`）
- 知识库保留了原文措辞，只做了三件事：加章节标题、补章节号、合并 Word 的硬换行。
- 原文有 53 张图片（举报流程图、出生点判定图、撤离点界限图、单向门区域图），**文字提取不到范围**。
  知识库已在对应位置插入 `【图片缺失】` 占位，提示词里也明确要求模型不得脑补。要补全请人工加上图注文字。

## 二、部署步骤（以 AstrBot 为例）

> 本项目不依赖 AstrBot：`kb/` 是标准的 Markdown 知识库语料，`prompt/01/03` 是通用判定准则与速查表——在 Dify、FastGPT 等平台上传 kb/ 全部文件、把 prompt/02 的核心内容设为系统提示词即可等价复刻。下文仅以当前生产环境 AstrBot 为例。

1. **建知识库**：AstrBot 网页端 → 知识库 → 新建 → 上传 `kb/` 下全部 `.md`。
   - 分块：`.md` 按 Markdown 标题切分（只识别 `#`~`####`，h5/h6 不识别），父标题路径会拼进块文本；`分块大小`保持默认 512。`分块重叠`只在单个 section 超过 512 字符被按行递归切分时生效，按标题正常切出的块之间没有重叠——调大它连接不了相邻条款，保持默认即可（速查层文件已卡片化，每张卡片独立成块，不依赖上下文）。
   - 检索数量：`稠密检索数量`、`稀疏检索数量`默认 50，只是重排前的候选池大小，一般不用动；重排后最终注入对话的条数由 `最终返回结果数` 控制，默认 5，建议调到 8~12（多路召回 + 重排后容量太小容易漏条款）。
   - 检索管线：稠密 + 稀疏各 50 → RRF 融合取前 20 → 重排序模型重排 → 按 `最终返回结果数` 注入。重排请求失败会静默降级为融合排序结果、仅在日志留 warning——回答质量突然下降时先查日志。
   - 模型建议：嵌入 text-embedding-v4（单条上限 8192 token，维度建库时固定，创建后不可改）+ 重排 qwen3-rerank。
2. **设人格**：把 `prompt/02-系统提示词.md` 中 `---8<---` 之间的内容整段粘贴到人格（persona）里。
3. **挂知识库**：在该人格 / 会话设置中启用上面建的知识库。
4. **触发方式**：QQ 群里建议用 @ 或唤醒词触发，不要开启全量自动回复——规则问答是低频刚需，自动回复会误伤日常聊天。
5. **回复长度**：QQ 单条有长度上限，建议开启自动分段；系统提示词里已要求用纯文本而不是 Markdown 表格。
6. **（可选）卡片渲染**：另行安装 [astrbot_plugin_rule_card](https://github.com/wujunze/astrbot_plugin_rule_card) 插件，规则解释回复会自动转成 SCP 风格卡片图片，安装与 Docker 持久化见该仓库 README。

## 四、常见问题排查

**答非所问 / 引用错章节**
→ 知识库没按标题切分，或检索条数太低。先把 `kb/` 里对应文件单独开出来问一次，确认是检索问题还是模型问题。

**编造处罚**
→ 检查知识库里是否已上传 `kb/13-处罚速查.md`（与 `prompt/03-处罚速查表.md` 同源，已按知识库分块优化为条目式；它本身就是"禁止编造"的硬约束）。再跑 `04-回归测试用例.md` 中的 T13、T14、T15。

**把图片标注当规则解释**
→ 确认 `【图片缺失】` 占位没有被删掉；跑 T16。

**回答太长，群里刷屏**
→ 系统提示词中【输出格式】的情况 B 已限制长度；也可以在 AstrBot 里加一句"超过 300 字请先给结论"。

## 五、规则更新流程

**规则文档更新：**

1. 拿到新版 `规则.docx`，放到本目录外的工作目录（docx 本体不入库）。
2. 用内部转换脚本重新生成 `kb/`（脚本不开源；若章节行号变化，先更新脚本里的 `HEAD` 表）。
   > ⚠ **P0 待办未修，暂勿直接重跑**：脚本当前把第六章映射为单文件 `06-第六章-阵营职责规则.md`，与现行 kb 结构（`06-第六章-阵营职责规则（总则）.md` + 32 个 `06-阵营-*.md` 分文件）脱节，重跑会生成与线上结构冲突的重复大文件。速查层（00/09/10/11/12/13）为手工维护、不在脚本输出范围，重跑时注意不要误删。修复第六章拆章映射后再恢复本流程。
3. 对照 `kb/07-第七章-规则版本改动记录.md` 的最新条目，检查 `prompt/01-解释准则.md` 的 R10（版本与时效）和 `prompt/03-处罚速查表.md` 的 E 节是否需要增删。
4. 跑一遍 `prompt/04-回归测试用例.md`，全绿后再替换线上知识库。

**人物文档更新：**

1. 拿到新版人物介绍 docx，放到本目录外的工作目录。
2. 重新提取纯文本到 `_chars_raw.txt`（沿用 python-docx 按样式提取，`[Style] text` 格式）。
3. 用内部转换脚本重新生成 `kb/08-人物-*.md`（脚本不开源；新增分组需在脚本的 `META` 表登记映射，出生分组与阵营字段不一致的角色会自动加 ⚠ 标记）。
4. 核对 `kb/08-人物图鉴-总览.md`：分组↔阵营对照表、间谍清单、术语表是否需要同步增删。
5. 涉及阵营/关系变更时，同步更新 `kb/09-阵营关系速查.md`（关系段落原文照抄）。
6. 跑一遍 `prompt/04-回归测试用例.md` 的"六、人物图鉴"与"七、阵营关系双向核对"，全绿后把新增/变更的 08、09 文件上传线上知识库。
